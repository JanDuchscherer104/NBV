Candidate 1: Collapse Shallow One-File Folders

Strong

Files: logging/names.py, reporting/plotting.py, callers in app/Lightning/tests/docs.

Problem: These modules have nearly the same interface cost as their implementation. The extra package level adds no depth, no adapter variation, and weak locality.

Solution: Move them to rri_metrics/logging.py and rri_metrics/plotting.py. Keep them leaf imports, not root exports.

Benefits: Better locality and less import noise. The deletion test says these folders would vanish without spreading complexity.

Candidate 2: Make Rollout Metrics A Real Deep Module

Strong

Files: metrics/multi_step.py, metrics/multi_step_tables.py, metrics/torchmetrics_multi.py.

Problem: One module mixes rollout objective tensors, policy diagnostics, provenance sanity checks, DTOs, and helper reducers. Callers must know too much implementation detail.

Solution: Create rri_metrics/rollout/ with returns.py for core target-return tensors, diagnostics.py for candidate and acquisition-cost sanity checks, torchmetrics.py for stateful adapters, and tables.py for mapping/Streamlit adapters.

Benefits: The interface becomes the test surface: training/Q_H code imports from rollout.returns; audit code imports from rollout.diagnostics. This gives leverage without changing semantics.

Candidate 3: DTO Ownership By Producer Locality

Strong

Files: types.py, rollout DTOs, oracle DTOs, distance DTOs.

Problem: A global types module would become a shallow catalog. Current TODOs already show uncertainty about whether every DTO should be pulled away from the producer functions.

Solution: Keep cross-seam stable result contracts in types.py, including DistanceBreakdown for this pass. Colocate local return DTOs with producer modules: TorchRolloutMetrics in rollout.returns, diagnostic DTOs in rollout.diagnostics, and RootEvalPointCloud in oracle evidence.

Benefits: Maintainers find a DTO next to the function that produces it. The interface stays smaller while field docs carry shapes, units, and lifecycle semantics.

Candidate 4: Shrink Public Surfaces

Strong

Files: __init__.py, metrics/__init__.py, future rollout/__init__.py, API docs.

Problem: The root package is compact, but metrics.__all__ still exports 46 names and makes the package feel larger than the real stable interface.

Solution: Treat package __init__ files as navigation only. Export only stable scientific contracts at the root and force diagnostics/adapters through their leaf modules.

Benefits: Less accidental public interface. Tests can lock the few real seams instead of every helper.

Candidate 5: Typed TorchMetric State Contracts

Worth exploring

Files: metrics/torchmetrics_multi.py, metrics/torchmetrics_single.py.

Problem: Multi-step TorchMetric state is created dynamically through add_state, so generated docs and readers cannot see state shape or distributed-reduction semantics.

Solution: Add class-level typed attributes and inline docstrings for every state tensor, then enforce that pattern with a focused state-contract test. Keep this as a required cleanup step when moving classes to rollout/torchmetrics.py.

Benefits: Better generated API docs, stronger reviewability, and clearer test targets for stateful adapters.

Top Recommendation

Tackle the rollout deep module first, but include the shallow-folder collapse in the same execution package because it lowers import noise with low risk. Do not add another generic types/ subpackage. Use producer-local DTOs plus a small cross-seam types.py.

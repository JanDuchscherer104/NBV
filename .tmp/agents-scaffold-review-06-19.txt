Comprehensive Review of the ARIA-NBV Agent
Scaffold
What the scaffold is already doing well
The branch codex/full-rri-rollout-worktree has a coherent scaffold spine already. The root
AGENTS.md acts as a dispatcher, pushes non-trivial work through agent-behavior , routes to narrower
skills for context, KG, diagnosis, docs, memory, or cleanup, and explicitly keeps OMX optional rather than
making it a required operating layer. The source-order document, alignment-tools contract, and owner-
intent file reinforce the same core idea: .agents/ is the canonical scaffold, current truth lives in canonical
memory and source-order owners, public docs are a separate surface, and external tooling is advisory
rather than normative. 1


That high-level shape is also consistent with the backlog. The internal DB explicitly lists “Scaffold Hygiene,”
“Docs Discipline,” and “Agentic Lifecycle” as priority pillars, which means the repo already recognizes
scaffold quality as first-class engineering work rather than incidental polish. The open issues say the main
remaining debt is not lack of structure, but repeated ownership, hot-path overload, and inconsistent skill
metadata. In other words: the macro-architecture is mostly right, but the control plane is still too verbose
and too repetitive. 2


The skill inventory is also substantial and already partitioned along sensible boundaries. I counted nineteen
skills in .agents/skills/ , including universal router/control skills, domain-contract skills, docs/
authoring skills, visualization/inspector skills, and optional KG/tooling skills. That is not a toy scaffold
anymore; it is a real operating system for the repo. The fact that there is already a backlog item to “distill
agent scaffold ownership and DB record style” is a strong sign that the right next move is refinement, not
wholesale replacement. 3


The main structural problems
The clearest problem is metadata inconsistency across skills. Some skills use a rich frontmatter contract
with mode , not_when , handoff_to , evidence_required , must_read , and verification ;
others only declare applies_to , triggers , must_read , and verification . The open scaffold
issue explicitly calls for “one universal skill metadata floor plus optional broad-skill routing extras,” and the
refactor record repeats the same recommendation. This is the single most important scaffold change,
because once metadata is inconsistent, routing quality, validation quality, and future automation all
degrade. 4


The second problem is root-guide density. The current root file still carries domain guardrails such as V0 vs
V1 target rules, invalidity semantics, and Gym/SB3 scope constraints. Those rules are good, but they are too
specific for root routing. Your own refactor record recommends trimming root AGENTS.md down to repo-
wide operational invariants and moving V0/V1, invalidity, and Gym/SB3 gates into domain skills and thesis/




                                                        1
current-state sources. I agree completely. Root guidance should answer “how this repo routes and captures
durable state,” not “what ARIA-NBV thinks about target labels or simulator scope.” 5


The third problem is duplicated retrieval/routing policy around litkg. The scaffold already separates local
deterministic discovery ( aria-nbv-context ) from KG-backed routing and claim-checking ( aria-litkg-
memory ), and keeps KG implementation work inside semantic-scholar-litkg . That separation is
conceptually sound. But issue issue-023 says the litkg probation-router is still too noisy for default agent
use, and the alignment contract says litkg is only one advisory evidence channel and must not become a
hidden source of repo truth. So the current problem is not that the split is wrong; it is that the split is being
over-described in too many places. 6


The fourth problem is hot-path overload. Your own refactor record says docs/AGENTS.md ,
code-review , and simplification should be shortened on their hot paths, with long taxonomy and
choreography moved to optional references. That is exactly right. Any skill that is meant to be hit frequently
has to be fast to parse mentally. Today, the scaffold often over-explains before it routes. That creates
cognitive tax every time the system operates.     7




Which skills to keep, prune, merge, or restructure
The universal control-plane skills should stay, but they need sharper roles. agent-behavior should
remain the single universal preflight skill. It is already well-scoped: inspect owner, state assumptions, keep
diffs traceable, verify before done. Do not drop it. Instead, make it the thinnest mandatory layer and stop
repeating its principles elsewhere. agents-db should also stay, because the scaffold clearly wants
.agents/*.toml to remain the canonical active maintenance surface. plan-grill and diagnose-
aria also earn their place because they separate ambiguous high-impact planning from concrete failure
loops, which is a healthy distinction.   8




aria-nbv-context , aria-litkg-memory , and semantic-scholar-litkg should remain three
distinct skills, but their boundaries should be tightened. aria-nbv-context should be the default first
hop for localization. aria-litkg-memory should become explicitly non-default unless the task needs
source-backed routing, consolidation, or claim checks. semantic-scholar-litkg should stay
implementation-only. I would not merge them, because the implementation-vs-usage split is good; I would
instead reduce overlap and standardize when each one is allowed to arbitrate. The repo’s own issue about
noisy litkg output is evidence that this should be a demotion of scope, not a broader merger. 9


The docs and authoring cluster should remain split into docs-curator , typst-authoring , and aria-
nbv-mermaid . That is a good separation of concerns. docs-curator governs public/internal boundary,
Quarto navigation, and claim ownership. typst-authoring governs notation, citations, compile/render
QA, and prose discipline. aria-nbv-mermaid governs source diagrams, notation mapping, lint/render
loops, and figure assets. These are genuinely different workflows. What should change is not the split, but
the hot-path length: make docs-curator a short router/boundary skill; leave deep writing doctrine in
typst-authoring ; and let Mermaid stay figure-specific.        10




The domain-contract cluster should mostly stay intact. entity-aware-rri , nbv-geometry-
contracts , counterfactual-rollout-planner , dataset-cache-ops , rerun-nbv-inspector ,
and lrz-ai-systems are all strongly tied to separate technical contracts and verification loops. These are




                                                        2
not arbitrary micro-skills; they encode different invariants, different tests, and different failure modes. Keep
them. The same is true for python-docstrings , though I would demote it from any broad routing
priority and treat it as a utility skill that should only trigger when documentation contracts are explicitly
being edited. 11


simplification should stay, but be cut down hard. It is valuable because it encodes a pruning ethos
that the branch explicitly wants, and the backlog names scaffold simplification as a live need. But its
practical role is narrow: behavior-preserving deletion, de-duplication, and surface reduction. It should not
read like a second general operating manual. Keep it as a surgical cleanup skill, not a parallel philosophy
text. 12


code-review should stay, but I would normalize it immediately. The directory is code-review , while
the metadata name is code-review-aria-nbv . That kind of mismatch is small, but it is exactly the kind
of inconsistency that accumulates into routing friction. More importantly, your refactor backlog says PR and
issue lifecycle skills still need to be ported, which means code review currently exists without an equally
strong PR workflow layer. Keep the review skill, but stop letting it stand in for full collaboration workflow
coverage. 13


The most important missing skills are already named in your own backlog: oracle-rri-contracts and
vin-training-eval . I would add both. The first closes a gap between geometry/RRI/oracle semantics
that is currently distributed across multiple skills and AGENTS files. The second gives you a clean home for
resumed VIN experimentation, diagnostics, W&B/Optuna, and evaluation rituals when that branch of work
reactivates. Those are real missing skills, not speculative ones.   14




The concrete scaffold redesign I would make
I would reorganize the scaffold into three tiers.


The first tier is a very small control plane: agent-behavior , aria-nbv-context , diagnose-aria ,
plan-grill , agents-db , and docs-curator . These are the only skills that should feel “top-level.”
Everything else should be a second-hop domain or utility skill. That change would align with your own
stated goal to keep root routing simple and keep domain guardrails out of root. 15


The second tier is domain-contract skills: geometry, rollout planning, dataset/cache ops, entity-aware RRI,
Rerun inspector, LRZ systems, Typst authoring, Mermaid, and semantic-scholar-litkg. These should never
have to explain general scaffold policy. They should only encode domain invariants, must-read surfaces, and
verification loops. The more domain-pure they are, the better they will age. 16


The third tier is utility and workflow add-ons: python-docstrings , simplification , plus new skills
for GitHub lifecycle, pandas data science, and Plotly visualization. These should be discoverable and useful,
but never part of the mandatory routing spine. That matches the owner-intent file, which explicitly prefers
compact ARIA-native skills over vendoring a giant generic skill wall. 17


I would also add one repo-level skill metadata contract and enforce it mechanically. The minimum
frontmatter should be name , description , applies_to , triggers , must_read , and
verification . Optional fields such as mode , not_when , handoff_to , and evidence_required




                                                        3
should only be allowed for broad router/control skills. This is exactly what your open issue and refactor note
are asking for, and it would make the skill set much easier to validate, lint, and eventually bridge into other
agent runtimes. 18


The new skills I would add next
The first new skill should be a GitHub collaboration skill, probably split into github-pr-lifecycle and
github-issue-triage , or implemented as one compact github-collaboration skill with two
modes. You already have an open issue saying the GitHub collaboration scaffold is incomplete, and the
refactor backlog says PR and issue lifecycle workflows still need to be ported. The repo should have a first-
class answer for draft PR policy, issue templates, review threading, labels, and what gets mirrored from
local .agents/*.toml to GitHub and when. 19


The second new skill should be oracle-rri-contracts, exactly as already proposed in the backlog. Right now,
RRI/oracle semantics are spread across geometry, entity-aware RRI, dataset handling, and thesis sources.
That is manageable for experts, but unnecessarily fragile for agent routing. A dedicated contract skill would
reduce accidental semantic drift around frames, units, binning, target-vs-scene semantics, and reporting
language. 14


The third new skill should be vin-training-eval, again exactly as already proposed. The backlog says it
should remain deferred until VIN work resumes, which is the right call. But it should exist as soon as the
work resumes, because experiment workflows, diagnostics, validation gotchas, W&B/Optuna, and score
interpretation are too specific to leave diffused across package AGENTS files.    14




The fourth and fifth new skills should be the ones you asked for directly: pandas-data-science and plotly-
data-viz. These should not be generic “Python data” skills. They should be built the same way your best
current skills are built: explicit task modes, preferred tools, decision rules, chart/table/report defaults, and
verification/output expectations. More on concrete external implementations below. 20


The best external skill implementations to adapt for pandas and
Plotly
For skill packaging and authoring discipline, the three best public references I found are Anthropic’s
official skills repository, Posit’s skills repository, and Treasure Data’s td-skills repository.
Anthropic’s repo is the canonical public reference for the skill format itself. Posit’s repo is especially strong
on keeping skills focused, pushing category-level context into READMEs instead of bloating every individual
skill directory, and documenting contribution principles. Treasure Data’s repo is strong on plugin packaging,
release channels, and trigger tests, which is exactly the kind of governance your scaffold should borrow if
you want skill quality to remain stable as the set grows. 21


For a pandas-oriented skill, the best public implementation to adapt structurally is Treasure Data’s pytd
skill, not because you need the TD-specific APIs, but because it is written as a true analytical workflow skill
rather than a loose cheat sheet. It covers installation assumptions, dataframe import/export, ETL patterns,
chunked processing for large results, writer choices, and concrete failure-handling patterns. That style is
much closer to what you want than a generic pandas syntax summary. Pair that with Streamlit’s official




                                                        4
displaying-streamlit-data skill, which is very good on dataframe presentation choices, column
configuration, hiding sensitive columns correctly, and choosing the right display primitive for the job. Then
enrich those two patterns with official pandas-adjacent tools: pyjanitor for pipe-friendly cleaning verbs,
fg-data-profiling for one-line EDA reports, and great_tables for publication-quality tables.                      22




My recommendation is to build pandas-data-science with five submodes: load-validate , clean-
transform , eda-profile , table-reporting , and scale-memory . In load-validate , teach
chunked IO and dtype discipline from pandas IO guidance. In clean-transform , prefer method chains
and pyjanitor -style declarative cleaning. In eda-profile , allow fast profile reports through fg-
data-profiling . In table-reporting , default to great_tables or pandas Styler for polished
outputs. In scale-memory , require chunking, sampling, or query pushdown before materializing huge
frames. That would give you a serious data skill instead of a generic notebook helper.         23




For a Plotly skill, the best external implementation to adapt directly is Treasure Data’s visualization skill. It is
concrete, opinionated, and operational: no subplots for ordinary analysis, strict chart-level QA, explicit
legend visibility, mandatory text labels for bars and heatmaps, and JSON/object structure discipline for
downstream rendering. Even if you do not want their brand palette, the chart QA logic is excellent. Pair that
with Plotly’s official docs on the Express vs graph_objects split, so the skill knows when to use the terse
dataframe-first API and when to drop to low-level control. For time-series scale, add plotly-resampler ,
which is specifically built to keep large time-series figures responsive by aggregating relative to the visible
range. 24


I would build plotly-data-viz with four submodes: express , graph-objects , resampler , and
embed . express is for rapid dataframe-native charts. graph-objects is for composed multi-trace
scientific figures. resampler is mandatory when time-series scale gets large enough that ordinary Plotly
becomes sluggish. embed should contain the app-specific integration rules for Streamlit or marimo. If this
skill is intended for Streamlit surfaces in particular, start from Streamlit’s official data display skill, but
deliberately override its Altair-first bias with your own Plotly-first rule. 25


The external tool implementations I would adopt for the broader
scaffold
For GitHub integration, I would prefer GitHub’s official MCP server over any homegrown GitHub wrapper
whenever possible. GitHub’s official server is explicitly built for repository intelligence, issue and PR
automation, CI/CD inspection, and security workflows. More importantly, GitHub’s own guidance strongly
recommends read-only mode and selective toolsets for safer operation, which fits your alignment-tools
contract and your desire to keep external tools advisory rather than unconstrained sources of mutation.
 26




For browser automation, I would standardize on Microsoft’s Playwright MCP. It is the official Playwright
MCP implementation, it uses structured accessibility snapshots rather than pixel-only interaction, and the
Playwright documentation explicitly positions it as the MCP path for browser automation in agentic clients.
Given that your current scaffold already contemplates interactive app inspection for Streamlit symptoms,
this is the cleanest maintained external implementation to anchor on. 27




                                                          5
For generic MCP building blocks, I would treat modelcontextprotocol/servers as the baseline
reference set. It is the official reference-implementation collection for MCP servers. That does not mean you
should import everything blindly. It means your custom tools should justify themselves against a known
maintained baseline first. If a standard server already covers a capability, your scaffold should prefer
adaptation or thin wrapping over bespoke reinvention. 28


For code indexing and structural search, I would seriously consider using ast-grep and
tree-sitter underneath or beside your current code-index layer. ast-grep gives syntax-aware
structural search and rewrite; tree-sitter gives incremental parsing and syntax trees suitable for
navigation, refactoring, and structural search. If your current code-index is mostly lexical plus some symbol
summaries, these two projects are the most credible maintained external foundation for making it more
precise without turning it into a giant bespoke system. Sourcegraph becomes interesting only if you want
large-scale cross-repo search, exact diff history, or external hosted code search beyond local repo analysis.
 29




For tool governance, I would not add another major framework yet. Your own alignment contract already
says autoresearch adapters should be replaceable, proposal-only, and built around bounded typed tools
rather than raw shell by default. The refactor backlog explicitly says not to add LangGraph, LlamaIndex, or
similar dependencies until a later dependency gate chooses them. I agree. The immediate need is not
another framework. The immediate need is a repo-owned tool registry and a consistent risk model. 30


The concrete change I would make is to extend the existing alignment-tools contract into a lightweight tool
registry. For every tool or MCP server, record: owner, read-only vs mutating, auth mode, typical latency,
output type, trusted use cases, forbidden use cases, fallback if unavailable, and whether its outputs are
advisory evidence or durable repo-owned truth. GitHub’s hosted MCP server already exposes the right
philosophy here with selective toolsets and read-only mode; your scaffold should mirror that same
explicitness across every external tool. 31


Recommended end state
The best end state is not “more skills.” It is a smaller top-level scaffold, cleaner metadata, stronger
domain skills, and better external specialization.


I would aim for this operating model: root AGENTS.md becomes short and invariant-only; a universal
metadata floor is enforced for all skills; control-plane skills are reduced to six or so top-level first hops;
domain skills keep their technical authority; KG is clearly advisory and not default-routing for localized work;
GitHub lifecycle becomes first-class; pandas and Plotly become first-class; and external tools are integrated
through a typed, risk-aware registry rather than ad hoc convenience. That recommendation is not
speculative; it follows almost line-for-line from your own open issue issue-012 , your litkg-noise issue
issue-023 , your owner-intent rules, and your refactor records for scaffold distillation, GitHub lifecycle,
Claude-first surfaces, and tool-boundary discipline.   32




If I compress this into a blunt verdict: do not replace the scaffold; distill it. The architecture is already
strong enough. The real work is pruning repetition, moving policy to single owners, standardizing
metadata, filling the obvious missing skills, and adopting maintained external implementations where the

repo is currently reinventing generic capability. That is the shortest path to a scaffold that is easier to route,
easier to validate, easier to port across agent runtimes, and much less likely to drift. 33
